# Xray Checker — мониторинг больших Xray-подписок через сеть iPhone

Xray Checker проверяет сотни прокси-привязок из российской мобильной сети и
показывает, какие серверы работают, стали нестабильными, сменили адрес или,
вероятно, требуют замены. Mac при этом продолжает пользоваться своим обычным
Wi-Fi: мобильный маршрут изолирован внутри отдельной виртуальной машины Colima.

[English version](README.md)

## Для чего нужен этот репозиторий

Проект предназначен для практического обслуживания Xray-подписок:

- проверить доступность всех привязок именно из мобильной сети iPhone;
- быстро заметить новые и изменившиеся адреса в подписках;
- отличить единичный сетевой сбой от повторяющейся ошибки;
- увидеть, какой IP использовался раньше и на какой он изменился;
- вручную перепроверить отдельную привязку или глубоко диагностировать ноду;
- сохранить результат при кратком отключении iPhone или пересоздании Colima;
- при необходимости экспортировать текущее состояние в Prometheus.

Это не ICMP ping, не проверка через Cloudflare, не `ipify` и не запрос к реестру
блокировок. Checker выполняет настоящий HTTP-запрос через каждую конфигурацию
Xray и отвечает на вопрос: «может ли эта привязка сейчас открыть контрольный URL
из сети, через которую маршрутизирована Colima?»

## Коротко: как проходит проверка

1. `start.sh` подключает отдельный профиль Colima `iphone` к USB-интерфейсу
   iPhone.
2. Go-приложение загружает подписки и строит конфигурацию Xray.
3. Xray создаёт локальный SOCKS5-порт для каждой проверяемой привязки.
4. Через каждый SOCKS5-порт Go-клиент делает два HTTP `GET` к
   `captive.apple.com/hotspot-detect.html`.
5. Хотя бы один корректный ответ с текстом `Success` означает, что привязка
   работает. Для задержки сохраняется лучший time-to-first-byte.
6. Результат попадает в веб-панель, JSON API, историю мониторинга и метрики
   Prometheus.
7. После полной проходки checker не запускает новый массовый цикл: он проверяет
   ноды по индивидуальному расписанию и немедленно реагирует на изменения
   подписок.

## Архитектура

```text
macOS (обычный Wi-Fi остаётся основным маршрутом Mac)
│
├── start.sh / stop.sh / iphone-supervisor.sh
│
└── Colima profile: iphone
    │ default route: col0 → iPhone USB → мобильная сеть
    │
    ├── network-monitor
    │   └── прямой GET к captive.apple.com через интерфейс col0
    │
    └── xray-checker (Go)
        ├── получает подписки
        ├── запускает и обновляет Xray
        ├── SOCKS5 :10000 + index для каждой привязки
        ├── GET: мобильная сеть → прокси → captive.apple.com
        ├── веб-панель и JSON API на 127.0.0.1:2112
        └── /metrics для внешнего Prometheus
```

Через iPhone идёт трафик виртуальной машины и её контейнеров. Сам Mac не
переключается на мобильную сеть целиком.

## Компоненты

### Go-приложение `xray-checker`

Основной процесс написан на Go. Он:

- загружает и разбирает подписки;
- строит топологию `Host ↔ Node`;
- запускает Xray и обновляет его конфигурацию;
- планирует массовые, адресные и ручные проверки;
- хранит текущий результат, историю ремонта и диагностику;
- обслуживает HTML-панель, JSON API и `/metrics`.

### Xray

Xray реализует сами протоколы VLESS, Reality, TLS, Hysteria и другие. Checker не
пытается воспроизвести их самостоятельно. Для каждой конфигурации Xray создаёт
локальный SOCKS5-вход, а Go отправляет контрольный HTTP-запрос через этот вход.

### `network-monitor`

Отдельный контейнер каждые 3 секунды проверяет Apple URL напрямую через `col0`.
Он записывает состояние `connected`, `recovering` или `waiting` в общий файл.
Если iPhone пропал, Go-процесс ставит новые проверки на паузу и не превращает
обрыв кабеля в сотни ложных `Offline`.

Если запрос к прокси оборвался одновременно с потерей мобильного маршрута,
checker ждёт подтверждения от `network-monitor`, восстанавливает соединение и
повторяет запрос без сохранения ложной ошибки.

### `iphone-supervisor.sh`

Это LaunchAgent macOS для аварийного восстановления. Когда iPhone снова
подключён, но маршрут `col0` не восстановился примерно за 15 секунд, supervisor
пересоздаёт bridge и профиль Colima. Между такими попытками действует cooldown
60 секунд.

В recovery-режиме сохранённый снимок результатов не удаляется, поэтому панель
возвращается без новой полной проходки.

## Host, Node и Binding

Checker хранит отношение многие-ко-многим:

- **Host** — запись подписки/inbound. В его идентичность входят название,
  подписка, протокол, transport и security, но не IP сервера.
- **Node** — физический endpoint, сгруппированный по IP/hostname. Порт не входит
  в `NodeID`, поэтому несколько inbound-портов одной машины относятся к одной
  ноде.
- **Binding** — конкретная проверяемая связь `Host + Node + Port`.

Отсюда следуют два нормальных случая:

- несколько похожих хостов Reality/TLS/Hysteria могут указывать на одну ноду;
- один хост может по очереди получать несколько нод из серверного пула.

Результаты хранятся на уровне binding: разные inbound одной машины могут вести
себя по-разному. `StableID` позволяет не перепутать одинаково названные карточки.

В панели осталось одно представление `Hosts`: оно показывает binding по записям
и группам подписок. Внутренняя модель Node продолжает работать на backend: на
ней основаны диагностика, групповые re-check, группировка алертов и отслеживание
общих IP, хотя отдельной вкладки Nodes в интерфейсе больше нет.

## Как загружаются подписки

При старте подписки читаются один раз для создания Xray-конфигурации. Затем
checker запускает цикл обновления каждые 60 секунд.

Каждый минутный цикл:

1. запрашивает все источники подписок;
2. делает четыре независимых снимка подряд;
3. объединяет встреченные endpoint для каждого хоста;
4. сравнивает новую топологию с текущей;
5. безопасно перезапускает конфигурацию Xray только при реальном изменении;
6. немедленно проверяет до 50 новых и изменённых binding;
7. отдельно проверяет изменения DNS для hostname-endpoint.

Источники нескольких подписок загружаются параллельно. В локальном профиле
включён JSON-режим и передаётся `X-Hwid`, чтобы совместимые панели возвращали
полные конфигурации и отдельные outbounds balancer.

Если один refresh обнаружил больше 50 затронутых binding, остаток сохраняется в
очереди due и обрабатывается scheduler пачками до 50. Это не позволяет одному
массовому изменению панели перегрузить мобильный канал.

### Можно ли получить все ноды хоста одним запросом

Это зависит от ответа панели:

- если JSON содержит все outbounds balancer, checker получает их за один раз;
- если сервер подписки сам случайно выбирает один IP и отдаёт только его,
  остальных адресов в ответе нет. Узнать невидимые адреса единоразово нельзя.

Для случайного пула четыре снимка в минуту работают как выборка. Все увиденные
`Host + Endpoint` накапливаются. Для равномерного пула из десяти нод полный набор
обычно обнаруживается примерно за 7–8 минут, но гарантии полноты нет: редкая нода
может появиться значительно позже. Детерминированный список возможен только
через отдельный API/базу панели, если они доступны.

Endpoint удаляется из накопленного пула после 30 успешных минутных циклов без
единого появления. Уже в первом пропущенном цикле он помечается missing и
скрывается из активного списка панели. Если точно та же привязка возвращается,
её история и последний статус восстанавливаются, после чего назначается свежая
проверка.

### Защита от ошибочного массового изменения

Если один ответ внезапно меняет не менее 100 существующих конфигураций без
обычных добавлений/удалений, checker не применяет его сразу. Одинаковая массовая
ревизия должна прийти в двух последовательных циклах. Это защищает от временно
повреждённого или неполного ответа панели.

## Обычная Apple URL Test-проверка

Для каждой binding используется отдельный SOCKS5-порт Xray. Go-клиент отключает
keep-alive и делает два независимых HTTP-запроса.

Успешным считается ответ, в котором одновременно:

- HTTP-код находится в диапазоне `2xx`;
- тело содержит ожидаемое слово `Success`;
- запрос действительно прошёл через соответствующий SOCKS5-порт.

Результат:

- `2/2` — чистый успех;
- `1/2` — online, но `Unstable`;
- `0/2` — ошибка;
- если первая массовая попытка провалилась, но медленная retry-пачка помогла,
  результат также считается `Unstable`.

Задержка — лучший time-to-first-byte из успешных запросов, а не ICMP RTT.
Географическое положение Apple не меняет точку происхождения: соединение с
прокси начинается из мобильной сети iPhone.

## Полная проходка

Обычный запуск `./start.sh` удаляет только `results.json`, собирает образ и
начинает новую полную проверку всех актуальных binding.

Проходка выполняется так:

- первая очередь — до 30 одновременных binding;
- каждая binding получает две быстрые Apple-попытки с таймаутом 4 секунды;
- только ошибки первой очереди переходят в retry;
- retry работает с параллельностью 10 и таймаутом 10 секунд на попытку;
- успешный retry заменяет исходную ошибку;
- завершённый снимок атомарно записывается в Docker volume.

Панель и API доступны уже во время проходки. После её завершения новая большая
проходка автоматически не запускается — продолжает работать адресный монитор.

## Адресное расписание после полной проходки

Scheduler просыпается каждые 10 секунд, выбирает до 50 binding, которым пора
провериться, и запускает их с ограниченной параллельностью.

| Текущее состояние | Следующая проверка |
| --- | --- |
| `Healthy` / `Fixed` | через 12–18 минут, распределённо по ID |
| `Unstable` | примерно через 4:30–5:30 |
| первая последовательная ошибка | через 1 минуту |
| вторая последовательная ошибка | через 2 минуты |
| третья ошибка, `Needs replacement` | через 5 минут |
| четвёртая и последующие ошибки | каждые 10 минут |
| первая чистая проверка после изменения | через 45 секунд |
| частичный успех после изменения | через 1 минуту |

Таким образом, ранее здоровая нода обычно обнаруживается быстрее половины
15-минутного интервала, в худшем случае — примерно через 18 минут. Статус
`Needs replacement` появляется после двух дополнительных подтверждений, то
есть примерно ещё через 3 минуты.

## Состояния мониторинга

| Состояние | Значение |
| --- | --- |
| `Unknown` | binding ещё не получила результат |
| `Healthy` | последняя обычная проверка прошла чисто |
| `Unstable` | прошла только часть попыток или помог retry |
| `Suspected` | одна или две последовательные ошибки; вывод ещё подтверждается |
| `Needs replacement` | не менее трёх последовательных неудачных раундов |
| `IP changed` | изменилась полная ревизия endpoint/credentials/transport или DNS |
| `Verifying new IP` | новая конфигурация проходит подтверждение |
| `Fixed` | после изменения получены два чистых успешных результата |
| `New IP failed` | новая конфигурация повторно не прошла проверку |
| `Missing` | binding не встретилась в последнем успешном цикле подписки |

Название `IP changed` историческое: ревизия может измениться из-за порта,
credentials, Reality/TLS-параметров или transport даже при прежнем IP.

## Ручной Re-check

Кнопка `Re-check now` запускает настоящую проверку немедленно и не ждёт конца
большой фоновой проходки. API отвечает только после готового результата, поэтому
индикатор `Rechecking…` соответствует реальной работе, а не постановке в очередь.

Параллельные запросы к одной и той же binding сериализуются: фоновая и ручная
проверка не могут одновременно перезаписать результат друг друга.

На уровне Node можно перепроверить сразу все связанные inbound. В один ручной
запуск берётся не более 50 binding.

## Глубокая диагностика Node

`Diagnose` — отдельная ручная процедура. Она не заменяет обычный health-статус
и не запускается автоматически.

Этапы:

1. проверить готовность маршрута iPhone и прямой Apple control request;
2. выполнить по три прямые попытки к endpoint-портам;
3. проверить TLS/Reality handshake для SNI из конфигурации;
4. сделать по три настоящих Apple GET через каждую Xray-binding.

Одновременно выполняется только одна глубокая диагностика. Она имеет приоритет
перед новыми фоновыми пачками. Хранятся последние 10 запусков на Node; отчёт по
старой конфигурации отмечается `Stale`.

| Verdict | Значение |
| --- | --- |
| `Healthy` | все binding прошли все три tunnel-попытки |
| `Degraded` | хотя бы одна binding работает, но не все получили `3/3` |
| `Port filtered` | контрольная сеть работает, но все TCP-попытки к endpoint провалились |
| `Handshake failed` | TCP доступен, но TLS/Reality handshake не завершился |
| `Tunnel failed` | endpoint доступен, но ни одна Xray-binding не провела control request |
| `Inconclusive` | маршрут/control недоступен, диагностика прервана или результат нельзя классифицировать |

`Degraded` не означает блокировку: это частичная работоспособность или
нестабильность. Смотрите счётчики попыток конкретных binding.

## Веб-панель

Панель доступна по адресу <http://127.0.0.1:2112>.

- `Auto` только обновляет данные API каждые 5 секунд; он не запускает проверки.
- После изменения HTML/CSS/JavaScript страницу нужно обновить один раз.
- Индикатор iPhone показывает `Connected`, `Recovering`, `Waiting` или
  `Monitor offline`.
- Клик по названию хоста копирует полное название вместо перехода в `/config`.
- `Copy IP` копирует адрес без порта.
- На карточке показано локальное время последней проверки в формате `HH:MM`.
- Строка `IP changed` показывает полный старый и новый адрес и переносится на
  следующую строку без обрезания.
- `Hosts` — единственное представление панели с записями подписок.

Порт Compose привязан к `127.0.0.1`, поэтому панель по умолчанию недоступна
другим устройствам локальной сети.

### Telegram-алерты

Кнопка с бумажным самолётиком в правом верхнем углу открывает мастер настройки:

1. создать бота через BotFather и вставить API token;
2. проверить токен;
3. отправить боту `/start`, после чего checker сам найдёт личный чат или
   группу;
4. сохранить получателя и отправить тестовое сообщение.

Сохранённый токен никогда не возвращается в браузер, не попадает в
`localStorage` и не выводится в логи. Он хранится отдельным файлом с правами
`0600` в persistent volume. В интерфейсе можно отдельно включать алерты о
подтверждённых сбоях, смене IP, восстановлении, неудачной проверке нового IP,
нестабильных нодах и восстановлении маршрута iPhone.

Уведомления отправляются по переходам состояния и группируются по физическому
endpoint. В одном сообщении перечисляются все затронутые хосты/inbound на этом
IP. Первая и вторая обычные ошибки остаются тихими; критический алерт появляется
по существующему порогу `needs_replacement` после трёх неудачных проверок.
Очередь, защита от дублей и последние отправленные состояния переживают
перезапуск checker.

Сообщения оформляются как компактные HTML-карточки на русском языке. IP-адреса
показываются моноширинным текстом для удобного копирования, а технические ошибки
переводятся в короткие причины: таймаут, закрытый порт, ошибка handshake или
неуспешный Apple URL Test. Для смены адреса используются отдельные события
`IP изменён`, `Новый IP работает` и `Новый IP не заработал`. Если за batch-окно
происходит несколько событий, бот отправляет один дайджест, сгруппированный по
критическим, нестабильным, изменившимся и восстановившимся нодам. В подробной
карточке отображаются не более трёх названий связанных хостов; остальные
сворачиваются в счётчик `+ ещё N`.

По умолчанию Telegram использует режим `Auto через здоровые Xray-ноды`. Отдельный
alert-worker читает последний готовый снимок checker, выбирает до трёх разных
физических нод и обращается к Bot API через их уже запущенные локальные
SOCKS-inbound. Сначала используется последний успешный маршрут; после ошибки он
временно охлаждается и пробуется следующая нода. Нода, о которой сформирован
алерт, исключается из маршрутов доставки собственного сообщения.

Доставка изолирована от health-check: она не запускает проверки, не меняет их
результаты, не занимает worker проверки и не ждёт в очереди checker. Если ни
одного здорового маршрута нет, сообщение остаётся в persistent-очереди до
следующей попытки. В панели также доступны `Direct` и отдельный пользовательский
HTTP(S)/SOCKS5-прокси. Credentials пользовательского прокси хранятся отдельным
файлом с правами `0600` и никогда не возвращаются в браузер.

## Go и Prometheus

Prometheus не выполняет проверки. Go-приложение проверяет прокси и хранит
последний результат, а затем публикует снимок в формате Prometheus на `/metrics`.

Основные gauge:

```prometheus
xray_proxy_status{protocol="vless",address="185.186.78.215:443",name="Sweden",stable_id="..."} 1
xray_proxy_latency_ms{protocol="vless",address="185.186.78.215:443",name="Sweden",stable_id="..."} 1187
```

- `xray_proxy_status`: `1` — online, `0` — offline;
- `xray_proxy_latency_ms`: задержка последней проверки, `0` при ошибке;
- labels включают `protocol`, `address`, `name`, `sub_name`, `stable_id`,
  `group_name`, необязательный `instance` и безопасные пользовательские
  `metricsLabels`.

При каждом scrape Go формирует метрики из текущего списка binding. Scrape не
пингует серверы и не изменяет расписание. Если Prometheus читает `/metrics`
каждые 15 секунд, между реальными проверками он получает одно и то же последнее
значение.

В `compose.yaml` нет сервера Prometheus и Grafana. Checker только предоставляет
совместимый endpoint. Внешний Prometheus можно настроить на pull с
`127.0.0.1:2112/metrics`. Также код поддерживает `METRICS_PUSH_URL`, но в локальном
профиле он не задан.

Веб-панель не зависит от Prometheus и читает JSON API напрямую.

## Какие данные сохраняются

Именованный volume `xray-results` монтируется в `/app/data`.

| Файл | Содержимое | Обычный `./start.sh` |
| --- | --- | --- |
| `results.json` | последний online/latency/error каждой binding и флаг завершённой проходки | удаляется для новой полной проверки |
| `node-history.json` | состояния ремонта, смены конфигурации и последние 40 событий | сохраняется |
| `node-diagnostics.json` | последние 10 ручных диагностик каждой Node | сохраняется |
| `telegram-settings.json` | получатель и настройки Telegram без секрета | сохраняется |
| `telegram-settings.token` | токен Telegram-бота с правами `0600` | сохраняется |
| `telegram-settings.proxy` | необязательный прокси Telegram с правами `0600` | сохраняется |
| `telegram-settings.state.json` | очередь и защита алертов от дублей | сохраняется |

Записи создаются через временный файл и атомарный rename. Остановка Compose без
удаления volumes не стирает историю.

## Первоначальная настройка

```bash
cp .env.example .env
```

Заполните `.env`:

```dotenv
SUBSCRIPTION_URL="https://example.com/one#ONE,https://example.com/two#TWO"

```

Fragment после `#` становится названием подписки в интерфейсе и не отправляется
серверу. Значение должно оставаться в кавычках, иначе `.env` воспримет `#` как
комментарий.

`.env` исключён из Git. Не публикуйте настоящие ссылки и HWID.

## Как найти USB-интерфейс iPhone

Подключите и разблокируйте iPhone, включите режим модема:

```bash
networksetup -listallhardwareports
```

Найдите `iPhone USB` и его `Device`, например `en7`. Это значение используется
вместо стандартного `en7`, если интерфейс отличается.

## Запуск

Обычный запуск с новой полной проверкой:

```bash
./start.sh
```

Другой интерфейс iPhone:

```bash
IPHONE_INTERFACE=en8 ./start.sh
```

`start.sh`:

1. проверяет `.env`, Colima, Docker, Compose и IPv4 iPhone;
2. останавливает старый профиль `iphone`;
3. запускает bridged vmnet через указанный USB-интерфейс;
4. убеждается, что default route виртуальной машины использует `col0`;
5. собирает образ;
6. удаляет только предыдущий `results.json`;
7. запускает `network-monitor` и `xray-checker`;
8. устанавливает LaunchAgent восстановления.

Панель: <http://127.0.0.1:2112>

## Перезапуск и восстановление

Разные команды имеют разную семантику:

| Действие | Полная проходка |
| --- | --- |
| `./start.sh` | да, `results.json` удаляется |
| автоматический recovery после возврата iPhone | нет, снимок восстанавливается |
| `docker restart xray-checker-xray-checker-1` | нет, используется volume |
| `docker-compose ... up -d --build --force-recreate` | нет, если снимок complete и соответствует текущим binding |
| изменение/добавление binding в подписке | проверяются только затронутые binding |

Если сохранённый снимок неполный или набор binding изменился, checker продолжает
только отсутствующую часть вместо повторения уже завершённых результатов.

## Остановка

Полностью остановить containers, Colima, vmnet-daemon и LaunchAgent:

docker-compose --context colima-iphone stop xray-checker

## Решение проблем

### `iPhone USB не подключён`

Разблокируйте iPhone, подтвердите доверие к Mac, включите режим модема и
переподключите кабель. Проверьте имя интерфейса через
`networksetup -listallhardwareports`.

### Панель показывает `Waiting` или `Recovering`

Пока маршрут не готов, проверки стоят на паузе. Проверьте:

```bash
docker-compose --context colima-iphone logs --tail 100 network-monitor
tail -f .runtime/iphone-supervisor.log
colima ssh --profile iphone -- ip -4 route show default
```

В default route должен присутствовать `dev col0`.

### iPhone вернулся, но соединение не восстановилось

Supervisor ждёт примерно 15 секунд, затем пересоздаёт Colima. Если этого не
произошло:

```bash
./iphone-supervisor.sh status
./start.sh
```

Ручной `./start.sh` начнёт новую полную проверку.

### Рабочая нода показывает `Failed`

Один успешный ручной клиент не гарантирует, что конкретная binding и Apple URL
работали в момент фоновой проверки. Нажмите `Re-check now` и смотрите время
результата. Checker сам подтверждает ошибки через 1 и 2 минуты; `Needs
replacement` не остаётся без проверки и повторяется каждые 10 минут.

WARP на выходе не мешает текущей Apple-only проверке: выходной IP не сравнивается.

### Сразу стало много `Offline`

Сначала проверьте `/api/v1/network`. Если iPhone оставался `Connected`, изучите
ошибки в логах. Большое количество `EOF`/timeout может означать перегрузку
мобильного канала. Уменьшите concurrency или временно верните более длинное
окно healthy-проверок.

### `Degraded`

Хотя бы одна Xray-binding провела настоящий запрос, но не все binding получили
`3/3`. Это не равнозначно блокировке. Откройте список Bindings в Diagnose.

### `Port filtered`

Контрольная сеть работает, но ни одна TCP-попытка к endpoint не прошла. Это
сильный сигнал фильтрации/недоступности порта, но причиной также могут быть
firewall, выключенный процесс или протокол только на UDP.

### Новый IP подписки долго не появляется

При полном JSON он должен появиться в ближайший минутный цикл. При серверной
рандомизации checker может увидеть только выбранный endpoint; четыре снимка в
минуту повышают вероятность, но не гарантируют полный пул за фиксированное время.

## Разработка и проверки

```bash
go test ./...
bash -n start.sh stop.sh iphone-supervisor.sh
sh -n network-watch.sh
docker-compose --context colima-iphone config --quiet
```

Основные пакеты:

- [`checker/`](checker/) — проверки, scheduler, история, diagnosis и pool;
- [`subscription/`](subscription/) — получение и parsing подписок;
- [`xray/`](xray/) — конфигурация и lifecycle Xray;
- [`web/`](web/) — UI, API и OpenAPI;
- [`metrics/`](metrics/) — Prometheus collector/push;
- [`models/`](models/) — идентичность Host/Node/Binding.

## Безопасность

- `.env` не должен попадать в Git;
- приватный API содержит endpoint и сгенерированные конфигурации;
- порт привязан к loopback и не должен публиковаться наружу без авторизации;
- при включении public mode используйте Basic Auth или доверенный внешний proxy;
- не прикладывайте subscription URL, HWID и полные diagnostic payload к публичным
  issue.
