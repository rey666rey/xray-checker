# Xray Checker — массовая проверка прокси через сеть iPhone

Этот репозиторий настроен для конкретной задачи: быстро проверять большую
подписку Xray из российской мобильной сети, пока сам Mac продолжает работать
через Wi-Fi.

Checker запускается в отдельной виртуальной машине Colima, основной маршрут
которой привязан к iPhone по USB. Он загружает все серверы из подписок,
проверяет их ограниченными пачками, повторяет неудачные попытки и сохраняет
готовый снимок результатов в локальной панели.

[English version](README.md)

## Что именно проверяется

Это не ICMP ping.

Для каждой ноды Xray поднимает локальный SOCKS5-порт. Через него checker делает
два HTTP `GET` к маленькой странице
`captive.apple.com/hotspot-detect.html`, измеряет время до первого байта и
оставляет лучший результат. Никакие сервисы определения выходного IP в health-
проверке не используются: хотя бы один корректный ответ Apple подтверждает,
что конкретная Xray-привязка работает.

Соединение с каждым прокси-сервером начинается именно из мобильной сети iPhone.
Оба запроса начинаются из мобильной сети iPhone. Расположение тестового сайта
не меняет исходную сеть теста: checker отвечает на практический вопрос
«открывается ли эта нода из текущей российской мобильной сети через Xray».

Режим по умолчанию рассчитан на большие подписки:

- все серверы проходят первую проверку пачками по 30;
- повторно проверяются только ошибки, пачками по 10;
- успешная повторная попытка заменяет первый неудачный результат;
- после завершения нет новых массовых проходок: проверяются только ноды, которым
  наступило время контрольной проверки;
- перезапуск checker начинает новый полный проход.

После полной проходки checker работает как очередь ремонта:

Checker хранит топологию многие-ко-многим. `Host` — отдельная запись
подписки/inbound, `Node` — физический endpoint/IP, а проверяемая привязка — их
пара. Поэтому Reality, TLS и Hysteria на одном IP проверяются раздельно, но в
панели объединяются под общей нодой. Один хост также может содержать пул из
нескольких нод.

- последовательные ошибки перепроверяются через 1, 2, 5, затем каждые 10 минут;
- три неудачных раунда переводят ноду в `Needs replacement`, но checker
  продолжает проверять её каждые 10 минут, поэтому восстановившаяся нода не
  останется ложным `Failed` на несколько часов;
- `Unstable` перепроверяется через 5 минут;
- стабильные ноды распределяются по окну 12–18 минут, поэтому новой большой
  пачки не возникает;
- подписки опрашиваются раз в минуту, но проверка запускается только для новых
  и изменившихся нод;
- два чтения подписки в каждом минутном цикле пополняют пул endpoint-ов хоста;
  чередование адресов `A → B → A → B` означает две активные ноды, а не шум;
- новый endpoint сразу добавляется и проверяется, а пропавший сразу скрывается
  из активной панели и удаляется после 30 успешных опросов без появления;
- если та же самая привязка вернулась без изменений, её история и последний
  статус сохраняются, но свежая проверка всё равно ставится в очередь;
- для статуса `Fixed` нужны два чистых успешных раунда через новую конфигурацию.

Основной вид панели — `Nodes`: один IP объединяет все привязанные хосты и
показывает, сколько inbound-ов работает. `Hosts` возвращает прежний вид по
записям подписки. Перепроверить можно как одну привязку, так и всю ноду. Ручной
`Re-check now` запускается приоритетно даже во время полной проходки, показывает
`Rechecking…` до готового результата, а карточка показывает время последней
проверки.

В закрытом виде `Nodes` также есть ручная кнопка `Diagnose`. Сначала она
подтверждает, что checker действительно вышел через контролируемую сеть, затем
делает по три TCP-попытки на реальных портах, TLS/Reality handshake для SNI из
подписки и по три настоящих GET через каждую Xray-привязку. Ручная диагностика
имеет приоритет перед новыми фоновыми пачками; если все TCP-порты недоступны,
она завершается без лишнего ожидания Xray-таймаутов. Результат хранится
отдельно от обычного health-статуса: `Healthy`, `Degraded`, `Port filtered`,
`Handshake failed`, `Tunnel failed` или `Inconclusive`. Сохраняются последние
10 запусков, а после изменения конфигурации старый отчёт помечается `Stale`.

Статус offline может означать, что прокси недоступен именно из текущей мобильной
сети, запрос превысил таймаут, прокси не смог открыть тестовый URL или мобильное
соединение прервалось во время проверки.

## Схема сети

```text
Панель на Mac: 127.0.0.1:2112
        │
        └── профиль Colima: iphone
                │ основной маршрут: col0
                └── режим модема iPhone по USB
                        │
                        └── мобильная сеть РФ → прокси-сервер → captive.apple.com
```

Через iPhone идут только виртуальная машина Colima и её контейнеры. Основной
маршрут самого Mac может оставаться на Wi-Fi.

## Требования

- Mac на Apple Silicon с macOS;
- Colima и Docker CLI;
- Docker Compose как плагин Docker или отдельная команда `docker-compose`;
- iPhone, подключённый по USB и отмеченный на Mac как доверенный;
- включённый на iPhone режим модема;
- ссылки подписок и HWID, который ожидает сервис подписки.

Готовая Compose-сборка рассчитана на `linux/arm64`.

В примерах ниже используется отдельная команда `docker-compose`. Если установлен
только плагин Docker Compose, заменяйте `docker-compose --context colima-iphone`
на `docker --context colima-iphone compose`.

## Первоначальная настройка

Создайте локальный файл окружения:

```bash
cp .env.example .env
```

Откройте `.env` и замените обе заглушки:

```dotenv
SUBSCRIPTION_URL="https://example.com/subscription#GROUP"
HWID="ваш-device-id"
```

Несколько подписок указываются через запятую:

```dotenv
SUBSCRIPTION_URL="https://example.com/one#ONE,https://example.com/two#TWO"
```

Часть после `#` становится названием группы в панели и не отправляется серверу
подписки. Оставляйте всё значение в кавычках, иначе `.env` воспримет `#` как
начало комментария.

Файл `.env` исключён из Git. Не добавляйте в коммит настоящие ссылки подписок
и HWID.

## Как найти интерфейс iPhone

Подключите и разблокируйте iPhone, включите режим модема и выполните:

```bash
networksetup -listallhardwareports
```

Найдите блок iPhone USB и значение `Device`, обычно это `en7`. По умолчанию
скрипт запуска использует `en7`.

## Запуск

Когда iPhone подключён:

```bash
./start.sh
```

Если USB-интерфейс называется иначе:

```bash
IPHONE_INTERFACE=en8 ./start.sh
```

Скрипт последовательно:

1. проверяет наличие `.env`, Colima, Docker, Compose и интерфейса iPhone;
2. при необходимости останавливает старый профиль Colima `iphone`;
3. запускает bridge-daemon vmnet, привязанный к USB-интерфейсу iPhone;
4. запускает Colima и проверяет, что основной IPv4-маршрут использует `col0`;
5. собирает и запускает Xray Checker и контейнер статуса маршрута в
   Docker-контексте `colima-iphone`;
6. устанавливает LaunchAgent macOS, который пересоздаёт bridge Colima, если
   подключённый iPhone не восстановился обычным способом.

При первой настройке vmnet macOS может запросить разрешение администратора.

После запуска откройте панель:

<http://127.0.0.1:2112>

Панель становится доступна сразу, пока результаты первой проходки ещё
постепенно заполняются.

Каждый обычный запуск через `./start.sh` удаляет снимок предыдущего запуска и
заново проверяет все ноды всех подписок. После завершения результаты хранятся,
пока работает контейнер, и дополнительно сохраняются только для безопасного
автовосстановления после обрыва iPhone.

## Как следить за проверкой

Состояние контейнера:

```bash
docker-compose --context colima-iphone ps
```

Логи в реальном времени:

```bash
docker-compose --context colima-iphone logs -f xray-checker
```

Проверка веб-сервера:

```bash
curl -fsS http://127.0.0.1:2112/health
```

Кнопка `Auto` в правом верхнем углу только включает и выключает обновление
панели через API; она не запускает проверку серверов. По умолчанию панель
обновляется каждые 5 секунд и показывает результаты фоновых адресных проверок
без ручной перезагрузки страницы.

Индикатор рядом с `Auto` показывает состояние маршрута iPhone. Фоновый монитор
проверяет доступность `captive.apple.com` именно через USB-интерфейс:

- зелёный — мобильный маршрут готов;
- жёлтый — USB-интерфейс доступен, маршрут восстанавливается;
- красный — checker ждёт подключения iPhone;
- `Monitor offline` — фоновый монитор перестал обновлять файл состояния.

Состояние отдельного контейнера-монитора можно посмотреть командой:

```bash
docker-compose --context colima-iphone logs -f network-monitor
```

## Как начать новую полную проверку

Обычный запуск всегда начинает новую полную проверку:

```bash
./start.sh
```

Прямой `docker restart` и автоматическое восстановление iPhone, напротив,
поднимают сохранённый снимок и не запускают все 844 проверки заново.

После изменения кода, `.env` или `compose.yaml` пересоберите контейнер:

```bash
docker-compose --context colima-iphone up -d --build --force-recreate
```

Отключение кабеля или переключение Wi-Fi на iPhone больше не требует ручного
перезапуска. Сначала запросы к прокси ставятся на паузу. Если vmnet нормально
подхватывает прежний lease, панель всё время остаётся доступна. Если старый
`col0` завис, macOS-монитор примерно через 15 секунд после появления телефона
сам пересоздаёт Colima. В этом запасном сценарии панель ненадолго пропадёт, а
затем вернётся с сохранёнными результатами без новой большой проходки.

## Как остановить всё полностью

```bash
./stop.sh
```

Скрипт выгружает macOS-монитор восстановления, останавливает монитор соединения,
удаляет Compose-контейнеры, останавливает виртуальную машину Colima `iphone` и
её bridge-daemon. Именованные тома `xray-geo` и `xray-results` сохраняются.

Остановить только checker, оставив Colima включённой:

```bash
docker-compose --context colima-iphone stop xray-checker
```

## Текущие настройки проверки

Локальные значения находятся в [`compose.yaml`](compose.yaml):

| Переменная | Значение | Назначение |
| --- | --- | --- |
| `SUBSCRIPTION_UPDATE` | `true` | Раз в минуту искать новые, изменённые и удалённые ноды |
| `SUBSCRIPTION_UPDATE_INTERVAL` | `60` | Интервал получения подписок |
| `SUBSCRIPTION_POOL_SAMPLES` | `4` | Снимков за цикл для быстрого обнаружения пулов нод |
| `SUBSCRIPTION_JSON_FORMAT` | `true` | Запрашивать полные JSON-конфигурации |
| `PROXY_CHECK_CONCURRENCY` | `30` | Размер быстрой параллельной пачки |
| `PROXY_CHECK_INTERVAL` | `600` | Интервал старого режима полных циклов; при `INITIAL_CHECK_ONLY` не используется для массовых проходок |
| `PROXY_INITIAL_CHECK_ONLY` | `true` | Выполнить один полный проход после запуска |
| `PROXY_CHECK_METHOD` | `urltest` | Два быстрых GET через прокси с лучшим результатом |
| `PROXY_URL_TEST_URL` | `http://captive.apple.com/hotspot-detect.html` | Основной маленький URL Apple |
| `PROXY_URL_TEST_ATTEMPTS` | `2` | Количество быстрых попыток |
| `PROXY_TIMEOUT` | `4` | Таймаут быстрой попытки в секундах |
| `PROXY_RETRY_TIMEOUT` | `10` | Таймаут повторной проходки ошибок |
| `PROXY_RETRY_CONCURRENCY` | `10` | Параллельность повторной проходки |
| `NETWORK_STATUS_FILE` | `/app/runtime/network-status.json` | Ставить проверки на паузу при потере iPhone |
| `NETWORK_STATUS_MAX_AGE` | `15` | Считать молчащий монитор offline через 15 секунд |
| `RESULTS_FILE` | `/app/data/results.json` | Сохранять готовую проходку при перезапуске checker/Colima |
| `NODE_HISTORY_FILE` | `/app/data/node-history.json` | Хранить состояния ремонта, смены IP и короткую историю между запусками |
| `NODE_DIAGNOSIS_FILE` | `/app/data/node-diagnostics.json` | Хранить последние 10 ручных глубоких диагностик каждой физической ноды |

Хотя бы один успешный Apple-запрос означает, что нода доступна. Если прошла
только одна из двух попыток или помогла повторная проходка, результат отмечается
жёлтым статусом `unstable`. Оставшиеся ошибки автоматически перепроверяются
отдельной медленной пачкой.

Если мобильный канал даёт много `EOF` или таймаутов, уменьшите параллелизм. Если
проверка стабильна, но идёт слишком долго, увеличивайте его постепенно. Чем
выше значение, тем больше одновременных соединений Xray и тем выше нагрузка на
радиоканал и NAT iPhone.

Все поддерживаемые переменные перечислены в
[`docs/src/content/docs/ru/configuration/envs.md`](docs/src/content/docs/ru/configuration/envs.md).

## Полезные адреса

| URL | Что находится |
| --- | --- |
| `/` | Локальная панель |
| `/health` | Состояние процесса; возвращает `OK` |
| `/metrics` | Метрики Prometheus |
| `/api/v1/public/proxies` | Текущий снимок для кнопки Auto |
| `POST /api/v1/proxies/{stableID}/recheck` | Немедленно перепроверить одну привязку и вернуть результат |
| `/api/v1/nodes` | Физические endpoint-ноды и все привязанные хосты |
| `POST /api/v1/nodes/{nodeID}/recheck` | Перепроверить все inbound-привязки одной ноды |
| `POST /api/v1/nodes/{nodeID}/diagnose` | Запустить глубокую диагностику из контролируемой сети |
| `GET /api/v1/nodes/{nodeID}/diagnosis` | Получить историю ручной диагностики ноды |
| `/api/v1/status` | Сводное состояние checker |
| `/api/v1/config` | Активная конфигурация без секретов |
| `/api/v1/network` | Текущее состояние маршрута iPhone |
| `/api/v1/docs` | Интерактивная документация OpenAPI |

Compose публикует порт только на `127.0.0.1`, поэтому панель недоступна другим
устройствам в локальной сети.

## Решение проблем

### Скрипт сообщает, что у iPhone нет IPv4-адреса

Разблокируйте iPhone, проверьте доверие к Mac, включите режим модема и
переподключите USB-кабель. Снова уточните имя интерфейса и при необходимости
передайте его через `IPHONE_INTERFACE`.

### Панель показывает Waiting или Recovering

Пока мобильный маршрут недоступен, checker не фиксирует затронутые запросы как
offline. Подключите и разблокируйте iPhone. Если обычное восстановление vmnet не
сработает, macOS-монитор сам перезапустит Colima. Его лог находится в
`.runtime/iphone-supervisor.log`. Если индикатор всё равно не становится зелёным,
посмотрите также логи сервиса `network-monitor` и проверьте имя интерфейса.

### Colima запускается, но checker не стартует

Посмотрите маршруты виртуальной машины:

```bash
colima ssh --profile iphone -- ip -4 route show default
```

В основном маршруте должно быть `dev col0`. `start.sh` специально не запускает
checker без этого маршрута, иначе тесты могли бы пойти через неправильную сеть.

### Результаты исчезли

Результаты хранятся в памяти. Перезапуск или пересоздание контейнера специально
очищает их и начинает новую полную проходку.

### Одновременно стало слишком много offline-серверов

Убедитесь, что iPhone оставался подключённым до конца проходки, и посмотрите
логи. Если большинство ошибок — таймауты или сбросы соединений, уменьшите
`PROXY_CHECK_CONCURRENCY` либо увеличьте `PROXY_TIMEOUT`, пересоберите контейнер
и повторите проверку.

## Происхождение проекта

Репозиторий основан на
[`kutovoys/xray-checker`](https://github.com/kutovoys/xray-checker) и сохраняет
его лицензию. Локальные изменения сосредоточены на стабильной идентификации
серверов с одинаковыми именами, ограниченных пачках, повторе ошибок,
одноразовом снимке результатов и изолированном запуске Colima через сеть iPhone.
