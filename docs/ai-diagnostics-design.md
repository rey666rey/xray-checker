# Проектный черновик: ИИ-диагностика хостов

Статус: предложение, без реализации и изменений в работающих сервисах.

Цель — воспроизводимо определить, на каком этапе соединение перестаёт
работать, сопоставить это с настройками Remnawave и дать объяснение с
проверяемыми основаниями. Измерения и проверку совместимости выполняет код;
модель объясняет собранные факты и ранжирует оставшиеся гипотезы.

## Что проверено в существующей системе

В конфигурации уже предусмотрена привязка подписки к панели Remnawave.
В `checker/diagnosis.go` есть контроль сети, TCP, транспортный TLS и
проверка реального туннеля через Xray. Есть история измерений и ревизии.
Подготовленные ранее изменения дают общий бюджет проб и кеширование
диагностики по эпизоду отказа; работающий контейнер ещё не обновлён ими.

13 октября 2026 получены ответы трёх панелей только следующими запросами:

| GET | Что доступно |
| --- | --- |
| `/api/hosts` | UUID хоста, адрес/порт, ссылки на профиль и инбаунд, ноды, переопределения SNI/Host/path/security, параметры XHTTP |
| `/api/nodes` | UUID ноды, состояние связи с панелью, версии, uptime, активный профиль и активные инбаунды |
| `/api/config-profiles/inbounds` | UUID инбаунда/профиля, protocol/network/security/port, rawInbound |

Выполнено 9 успешных GET, без иных методов и без переходов по редиректам.
Секреты и полные ответы не выводились и не сохранялись.

В профилях присутствуют RAW, XHTTP, TLS, REALITY и Shadowsocks. Это перечень
настроенных инбаундов, а не список всех работающих клиентских соединений.

## Одинаковый порядок действий для каждого запуска

### 1. Зафиксировать объект и контекст

Вход: привязка мониторинга, панель, время и причина запуска.
Единица результата — конкретный хост/инбаунд на конкретном endpoint.
Один Host может обслуживаться несколькими нодами; результаты сохраняются
раздельно для каждого endpoint, а сводка показывает частичную доступность.

Найти `panelID → hostUUID → profileUUID/inboundUUID → nodeUUID` и связать
с текущей конфигурацией из подписки. Текущие HostID и NodeID мониторинга —
локальные хеши, а не UUID Remnawave. Совпадения имени недостаточно:
сопоставлять также параметры соединения, адрес, порт и принадлежность панели.
Неоднозначность означает `mapping_ambiguous`, а не выбор первой записи.
Для первого MVP допустим явный выбор пользователем кандидата из панели.

Сохранить время каждого GET, хеши релевантной конфигурации, ревизию подписки,
версию Xray и версию плана проверок. Снимок нескольких GET не атомарен:
в конце перепроверить нужные объекты. При смене конфигурации результат
пометить устаревшим и назначить новый запуск.

### 2. Проверить пригодность измерительной сети

Проверить готовность интерфейса и маршрута, DNS и небольшие контрольные
GET к двум независимым заранее заданным адресам. Один неработающий контроль
не доказывает сбой всей сети. Сохранить исходящий IP и идентификатор сети.

Если сеть непригодна, остановиться с `measurement_unavailable`.
При изменении исходящей сети во время запуска не объединять результаты
в один вывод о блокировке.

### 3. Сверить панель с фактическим клиентским конфигом

Проверять эффективные параметры с учётом наследования и переопределений Host:

- существует ли выбранный инбаунд, активен ли он на соответствующей ноде;
- protocol, transport, security и совместимость с версией Xray;
- SNI и его переопределения, ALPN, flow;
- для REALITY — допустимость SNI и shortId, соответствие клиентского
  ключевого материала серверному; сравнение ключей выполняется локально;
- для XHTTP — path, Host, mode, extra-параметры и совместимость их сочетания;
- адреса DNS A/AAAA и ожидаемая схема подключения;
- состояние связи ноды с панелью, uptime и недавние изменения как контекст.

Порт Host может намеренно отличаться от порта inbound из-за прокси/CDN/NAT.
Адрес также может вести на промежуточный узел. Без описания схемы это
неизвестность, а не подтверждённая ошибка. Поле `node.port` нельзя принимать
за пользовательский порт Xray: оно относится к подключению панели к ноде.

`isConnected` панели не подтверждает доступность инбаунда для клиента и
не доказывает, что сервер исполняет именно прочитанную версию профиля.
Доступ пользователя к инбаунду тоже нельзя доказать одним rawInbound:
при отсутствии нужных данных это отдельный пробел, без выгрузки всех пользователей.
Если требуются routing/outbounds или раскрытие snippets, отдельно получить
нужный профиль документированным GET, поддерживаемым версией панели.

### 4. Выполнить короткий план сетевых проверок

План выбирает код по протоколу и имеющимся фактам. Стартовые ограничения MVP:
до 60 секунд на измерения, до двух диагностических проб одновременно,
повтор только неудачной пробы для подтверждения. Ограничения входят в общий
бюджет мониторинга, а не создают дополнительный независимый пул нагрузки.

| Слой | Действие | Что действительно измерено |
| --- | --- | --- |
| DNS | Разрешить A/AAAA, отдельно фиксировать путь к выбранным адресам | Какой endpoint проверяется; возможное расхождение DNS |
| TCP | Подключиться к клиентскому адресу/порту для TCP-транспорта | Доступность TCP с данной сети |
| TLS | Handshake с нужным SNI; для обычного TLS проверить имя, срок и цепочку сертификата с учётом настроек клиента | Ответ TLS и результат проверки сертификата |
| Протокол | Соединение действующим Xray-клиентом с реальными параметрами подписки | Возможность установить требуемое соединение |
| Туннель | Маленький GET через прокси с проверкой статуса/ожидаемого содержимого; второй контроль при отказе первого | Передача данных через туннель |

Обычный TLS handshake не проверяет аутентификацию REALITY: он может получить
ответ маскирующего сайта. В существующем транспортном TLS-пробнике отключена
проверка сертификатов, поэтому его результат не означает «сертификат корректен».
Отрицательная проба тоже не должна переопределять успешный полноценный туннель.
Для UDP нужен протокольный обмен; успешный UDP connect ничего не доказывает.

Неудачная проба одного инбаунда не переносится на остальные без измерений.
Неподдерживаемый протокол получает `unsupported`, а не `offline`.
Таймаут ограничивает знания: нельзя объявлять «сервер отверг авторизацию»,
если Xray сообщил только общий timeout.

### 5. При необходимости сравнить независимые пути

Сравнить тот же endpoint и ту же ревизию клиентского конфига из проблемной
мобильной сети и с независимого агента, если он настроен. Проверки делать
близко по времени, с сопоставимыми таймаутами и повтором отрицательного результата.

Дополнительно использовать уже измеренные соседние инбаунды: что работает
на той же ноде, IP, порту или SNI. Сетевые факты могут быть общими, но
вывод о работоспособности остаётся отдельным для каждого соединения.

«Работает снаружи, не работает с мобильной сети» подтверждает зависимость
сбоя от пути. Блокировка — возможное объяснение вместе с маршрутизацией,
фильтрацией на сервере и другими причинами. Без второй точки причина
сетевого таймаута часто остаётся неопределённой.

Доступность REALITY target с компьютера мониторинга не доказывает его
доступность с сервера. Без серверных измерений нельзя обещать точное
различение firewall, отсутствующего listener и проблем серверного выхода.

### 6. Сформировать факты, затем объяснение ИИ

Код выдаёт Evidence Bundle: нормализованные безопасные настройки,
результаты сверок и проб, времена, ревизии, источник измерений,
применимость каждого теста и причины пропусков.

Модель получает только этот пакет. API-токены, клиентские UUID/пароли,
REALITY privateKey и клиентский ключевой материал, сертификатные приватные
ключи, полные подписки и исходный rawInbound в запрос к модели не входят.
Вместо них передаются результаты локальных сравнений, например
`reality_key_matches: true`. Для группировки использовать локальный
необратимый идентификатор; отсутствие секретов не означает, что оставшаяся
топология перестала быть чувствительной — состав отправляемого пакета
должен быть прозрачен оператору.

ИИ не получает shell, токен панели или произвольный HTTP-инструмент.
Названия и описания объектов панели считаются данными, а не инструкциями.
Каждое объяснение ссылается на evidence ID; выводы без оснований отклоняются.
Текст ИИ не меняет машинный online/offline. При недоступности модели
остаётся обычный отчёт измерений.

## Шаблон итогового отчёта

```text
Объект: панель / хост / инбаунд / endpoint
Измерено: время, сеть, версия конфигурации
Доступность: работает / не работает с этой точки / нестабильно / неизвестно
Этап отказа: конфигурация / DNS / TCP / TLS / протокол / туннель / неизвестно

Подтверждено:
  - Факт + ссылка на измерение или конкретную сверку

Вероятные причины:
  - Гипотеза, уровень уверенности и факты в её пользу
  - Что ей противоречит и какие альтернативы остаются

Не хватает:
  - Какие данные отсутствуют; какие тесты пропущены и почему

Следующая проверка:
  - Одна конкретная безопасная проверка, способная различить гипотезы

Рекомендация оператору:
  - Что проверить или исправить вручную; ничего автоматически не применяется
```

Пример, не результат обследования реального хоста:
«Сеть контроля работает; TCP доступен; обычный TLS отвечает; настоящий
REALITY-туннель не передаёт данные. Клиентский shortId отсутствует среди
разрешённых в профиле. Подтверждено расхождение конфигураций; оно может
объяснять отказ. Не подтверждено, что нода применила текущий профиль.
Следующий шаг — сверить ревизию профиля на ноде и свежесть подписки».

## Поведение при волне отказов

- Обычный мониторинг имеет приоритет над обогащённой диагностикой.
- Метаданные панелей кешируются и перечитываются по необходимости,
  а не тремя запросами на каждый хост.
- Ключ повторного использования отчёта включает панель/хост/endpoint,
  ревизии панели и подписки, эпизод отказа, сеть и версию диагностического плана.
- Новая ревизия, новый отказ после восстановления, смена сети или
  противоречащее измерение инвалидируют соответствующие выводы.
- При большой очереди разбирать сначала характерные случаи каждого
  сочетания симптома/транспорта/сети. Похожие случаи получать общую
  гипотезу с пометкой «не проверено индивидуально».
- Ограничить частоту/стоимость запросов ИИ, объединять отчёт по волне,
  повторно анализировать только новые факты. Не делать вызов модели
  на каждую регулярную проверку.

## Предлагаемый первый выпуск

Ручная кнопка «Диагностика с ИИ» на карточке хоста. Один запуск выполняет
фиксированные шаги, показывает прогресс, обычный отчёт и объяснение ИИ.
Нет исправления конфигурации и автономного выбора произвольных команд.
Вторая точка измерения необязательна: если её нет, это явно отражено в выводе.

Порядок реализации: GET-клиент и сопоставление UUID → проверка параметров
и Evidence Bundle → уточнение протокольных проб → шаблон отчёта → ИИ → UI.
Автоматическое обогащение волн — после проверки ручного режима на
известных случаях и оценки нагрузки.

GET-клиент панели содержит только именованные методы чтения и список
разрешённых маршрутов. На уровне транспорта любой метод кроме GET
отклоняется, редиректы запрещены. Исключены маршруты генерации ключей,
actions и любые административные операции, даже если где-либо они используют GET.
Секреты не попадают в ошибки, логи и отчёты. Если установленная версия панели
поддерживает scopes, отдельный read-only токен можно подготовить вручную.
В рамках разработки диагностики токены и права в проде не меняются.

## Критерии приёмки

Проверить известные случаи: несовпадение SNI/shortId/ключа, ошибка XHTTP path,
закрытый порт, сбой DNS, неверный сертификат, отказ контрольного сайта,
потеря сети, неоднозначное соответствие Host, смена профиля во время запуска,
один неработающий endpoint в пуле и отказ модели.

Обязательные свойства: только GET к панели; отсутствие секретов в пакете
ИИ и логах; ссылки на факты; успешный туннель не объявляется неработающим
из-за вспомогательной пробы; неисследованные случаи остаются неизвестными;
при сотнях отказов соблюдается общий бюджет и обычные проверки продолжаются.

Источники: [Remnawave API](https://docs.rw/api/),
[Hosts](https://docs.rw/learn-en/hosts/),
[Config Profiles](https://docs.rw/learn-en/config-profiles/),
[REALITY](https://xtls.github.io/en/config/transports/reality.html).
