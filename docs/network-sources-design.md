# Источники сети проверок: iPhone и LTE-роутер

Статус: grooming / предложение, 17 октября 2026. Код приложения и работающий мониторинг не изменены.
Макет использует демонстрационные адреса, а не данные подключённого оборудования.

## 1. Решение, которое предлагается обсудить

Ввести **«Источник сети проверок»**, а не ещё один специальный режим «модем».
Источник — именованный маршрут, через который выполняются прямые и Xray-проверки.
В первой версии активен ровно один источник: iPhone USB **или** отдельная сеть LTE-роутера.
Обычная сеть Mac не становится резервным источником измерений при обрыве мобильной сети.

Предпочтительная физическая схема для этой установки:

```text
Обычный Wi-Fi → Mac: повседневная работа и управление
LTE-модем → роутер с отдельной подсетью → выделенный Ethernet / USB–Ethernet Mac
                                               ↓ bridge Colima
                                      гостевой интерфейс Linux
                                               ↓
                         Xray + прямые сетевые проверки + DNS этих проверок
```

Модемом и SIM управляет роутер. Панель управляет профилем измерительного маршрута,
а не APN, SMS, прошивкой или перезагрузкой модема. CGNAT сам по себе не мешает исходящим
проверкам; входящие соединения из интернета для этой схемы не требуются.

Отдельный SSID полезен для организации сети, но не доказывает использование мобильного WAN.
Если тот же роутер при потере LTE переключает этот сегмент на проводного провайдера,
проверки продолжат работать уже в другой сети. Поэтому сегмент измерений должен быть
LTE-only либо роутер должен предоставлять достоверный WAN-status, используемый как gate.
IP/ASN внешнего адреса — вспомогательные признаки, а не достаточное доказательство LTE.

Если подключение планируется только по Wi-Fi, сначала проверить реальный bridge на
данной модели Mac/роутера. Один радиоинтерфейс обычно не даёт двух независимых подключений
к разным SSID одновременно; нельзя обещать сохранение домашнего Wi-Fi и отдельного LTE Wi-Fi
без второго интерфейса. Конкретную топологию согласовать после получения модели оборудования.

## 3. UX и состояния

### Основная панель

- Вместо «iPhone · IP» — «Сеть проверок · LTE-роутер · маршрут доступен».
- По нажатию: текущий источник, последний прямой публичный IP и его возраст,
  маршрут Mac → VM → шлюз, DNS, контрольные проверки, причина паузы.
- Отдельный экран «Сеть проверок»: профили, проверка кандидата и история переходов.
- «Проверить маршрут» не переключает сеть и не перепроверяет всю подписку.
- «Сделать активным» — отдельное подтверждённое действие с проверенным кандидатом.
- У LTE нет фиктивной кнопки «Переподключить iPhone»; доступна перепроверка пути.
- Публичный вид панели не раскрывает адрес шлюза, локальные интерфейсы и управляющие действия.

### Состояния источника (не состояния ноды)

| State | Отображение | Новые тесты / результаты |
|---|---|---|
| `disabled` | Источник выключен | Нет тестов |
| `waiting_link` | Нет подключения к выбранной сети | Пауза, старые измерения остаются историческими |
| `validating` | Проверяем маршрут | Пауза до завершения контрольных проверок |
| `ready` | Измерительный маршрут доступен | Тесты разрешены при выполненной политике источника |
| `degraded` | Частичные проблемы: DNS / один контрольный сервис | Селективный gate по нужным операциям; консервативно пауза в MVP |
| `no_internet` | Подключение к роутеру есть, внешний контроль не проходит | Пауза; это не массовое падение нод |
| `identity_unknown` | Путь работает, требуемый WAN не подтверждён | Пауза, если профиль требует проверенный WAN |
| `switching` | Переключение источника | Пауза и инвалидирование старых in-flight результатов |
| `stale` | Монитор маршрута не отвечает | Пауза независимо от последнего зелёного статуса |

Детали должны говорить «внешние контрольные запросы не проходят», а не уверенно
объявлять отказ модема. Отсутствие ответа ICMP само по себе не означает отказ шлюза.
Публичный IP контроля — **до VPN**; exit IP проверяемого VPN показывать отдельно.

## 4. Границы первой версии

Включить:
1. Именованные профили `iphone-usb` и `router-lan`, один активный источник.
2. Общий network-status и capability-aware UI вместо iPhone-specific строк.
3. Read-only discovery интерфейсов Mac и соответствия guest-интерфейсу.
4. Предварительную проверку кандидата без применения; ручное применение и полную
   проверку гостевого пути отдельным действием.
5. Строго заданный измерительный путь для TCP, TLS, Xray и DNS.
6. Сохранение и разделение результатов по источнику, session fencing, мягкий прогрев.
7. События паузы/возобновления/смены источника без потока ложных node alerts.

Отложить: параллельные операторы, автоматический failover между источниками,
удалённые probe-агенты, управление модемом, SIM/баланс/RSRP/SINR, AI-диагностику,
сравнительные графики нескольких сетей. Будущая интеграция с конкретным роутером
может добавить read-only WAN-status, но не является обязательной для LTE-only сегмента.

## 5. Под капотом

### 5.1 Конфигурация и наблюдения — разные сущности

`NetworkSourceConfig` хранит намерение: стабильный `id`, label, type,
host interface fingerprint/выбор, ожидаемую подсеть/шлюз, guest interface,
DNS policy, address-family, strict binding, WAN identity policy и capabilities.
Имя `en8` — полезное наблюдение, но не постоянная идентичность адаптера.
На старте интерфейс сопоставляется по сохранённым признакам, затем проверяется;
при неоднозначности профиль ожидает выбора, а не берёт «первый Ethernet».
MAC адрес и SSID не считаются криптографическим доказательством WAN.

`NetworkSourceStatus` хранит факт: `sourceId`, `configRevision`, `epoch`, `bootId`,
state/reason, host/guest interface, local IP, gateway, control checks,
public IP + `observedAt`, `wanIdentity={declared|verified|unknown}`, timestamps.
Публичные адреса, смена DHCP lease и результаты контроля не переписывают конфигурацию.
JSON пишется атомарно; consumer проверяет schema, epoch, TTL и аномальные future timestamps.
TTL freshness не переносится между рестартами; внутри процесса длительности монотонные.

Пример **контракта**, не существующий API:

```json
{
  "schemaVersion": 2,
  "sourceId": "router-mobile",
  "configRevision": "cfg-7",
  "bootId": "runner-boot-example",
  "epoch": "session-example",
  "state": "ready",
  "hostInterface": "en8",
  "guestInterface": "col0",
  "localIp": "192.168.8.30",
  "gateway": "192.168.8.1",
  "addressFamily": "ipv4",
  "publicIp": {"value": "203.0.113.42", "observedAt": "2026-10-17T09:00:00Z"},
  "wanIdentity": "declared",
  "strictBinding": true,
  "checks": {"egress": "pass", "dns": "pass", "control": "pass"}
}
```

`ready` при declared допустим только для явно настроенного LTE-only сегмента,
где пользователь принимает топологию как основание. При `requireVerifiedWan=true`
такой статус не ready. UI всегда показывает основание, а не выдумывает статус SIM.

### 5.2 Два уровня интерфейсов и границы маршрутизации

`hostInterface=en8` используется Colima bridge на macOS; `guestInterface=col0`
используют Linux Go/Xray. Совпадение имён не требуется и не предполагается.
Данные discovery приходят через host-supervisor; перечисление интерфейсов внутри
контейнера не обнаруживает физические адаптеры Mac.

Для текущей схемы достаточно одного проверенного bridge за раз. При смене физического
интерфейса может понадобиться остановка/запуск Colima, поэтому обещания бесшовности нет.
Не переименовывать профиль Colima `iphone` в первом релизе: это техническое имя,
с ним связан Docker daemon и его named volumes. UI label можно изменить независимо.

Развести control traffic и measurement traffic логически и затем маршрутно:
- измерения: direct endpoint probes, diagnostic TLS, Xray outbound, source-IP,
  DNS разрешения endpoint-доменов — только выбранный источник;
- служебное: загрузка подписок, Remnawave GET metadata, geo assets, Telegram —
  явная control-plane policy; никогда не выдавать результат служебного запроса
  за сетевое измерение. Текущая VM может предпочитать col0 для всего исходящего
  трафика, поэтому раздельный control-plane пока является работой, а не имеющимся фактом.

`SO_BINDTODEVICE` и Xray `sockopt.interface` сохраняются как обязательная защита.
Выбор шлюза нельзя заменить названием интерфейса или одним `sendThrough`.
Если на одном интерфейсе доступны несколько gateways, требуются явные policy routes
или отказ валидации неоднозначной схемы. DNS не должен уходить через системный
резолвер Mac/VM в обход binding: отдельный Go resolver (`PreferGo`, привязанный
`Dial`) и проверенная конфигурация DNS Xray/endpoint resolution. Учитывать UDP
и TCP fallback DNS, bootstrap и кэш с ключом контекста источника.

IPv4 — предложенный scope MVP, не глобальное выключение IPv6 на Mac. Все измерительные
пути принудительно используют выбранное семейство; AAAA/dual-stack не создают обхода.
Для более сложного multihomed-сценария следующий шаг — отдельный network namespace
измерений с собственными маршрутами/DNS и egress-правилами. Не навешивать общий kill-switch
на host namespace текущей VM: он может отрезать API и служебный трафик.
Проверить, что внешний `HTTP_PROXY`/`ALL_PROXY` и `NO_PROXY` не меняют контрольный путь.

### 5.3 Проверка маршрута

1. Host-adapter существует, однозначно выбран, link/IP соответствуют профилю.
2. Bridge получает адрес; guest route действительно направлен через ожидаемый gateway.
   До эксперимента проверить пересечения LAN с домашней сетью, Colima и Docker.
3. Выполнить минимум две небольшие независимые внешние контрольные проверки через
   этот интерфейс, с проверкой TLS/ожидаемого ответа; иметь IP-based контроль,
   чтобы DNS outage не выглядел как отсутствие физического подключения.
4. DNS проверить отдельным этапом. Один отказ контрольного сервиса — degraded,
   не автоматическое «все ноды заблокированы». Перечень целей должен подходить оператору;
   единственный Cloudflare endpoint не становится эталоном всего интернета.
5. Определить публичный IPv4 этим же путём и отдельно зафиксировать свежесть.
   Неуспех IP-info при успешных контролях — unknown IP, не обязательно no_internet.
6. Если WAN policy требует verified — получить поддерживаемый read-only статус
   роутера; без подтверждения оставить identity_unknown. По умолчанию нет авторизации
   к роутеру и нет утверждений о текущем LTE/5G, уровне сигнала или SIM.
7. После устойчивого восстановления открыть scheduler постепенно.

Предложение для настройки, не измеренные SLA: контроль раз в 5 с, timeout 3 с,
отдельный ограниченный бюджет; первая полная потеря контролей закрывает admission,
3 неудачных раунда подтверждают outage для уведомления, 3 успешных раунда открывают gate.
Heartbeat записывается независимо от продолжительности сетевых запросов; TTL 15 с.
Контрольные запросы идут параллельно и не используют очередь тысяч нод.
IP-refresh раз в 60 с; обнаружение CGNAT-ротации имеет соответствующую погрешность,
а не является мгновенным. Значения необходимо настроить после реального подключения.

### 5.4 Смена сети и защита от результатов из прошлого

Одного `Ready=true` в момент записи недостаточно: запрос мог начаться в сети A,
а закончиться после перехода в B. Ввести `ProbeContext`:

```go
type ProbeContext struct {
    SourceID       string
    ConfigRevision string
    Epoch          string // новый сеанс, включая reconnect с прежним public IP
    AddressFamily  string
}
// Схема commit, а не готовая реализация:
// lease := gate.Acquire(ctx)              // фиксирует контекст
// result := runProbe(lease.Context())
// store.CommitIfCurrent(lease, result)    // атомарно проверяет epoch + ready
```

Новая epoch: смена активного профиля, значимой config revision, runner restart,
подтверждённый reconnect/смена route identity и обнаруженная смена публичного IP.
Не создавать epoch на каждом heartbeat или каждом failed target probe.
Ключ отрицательного diagnostic cache включает source/config/epoch + binding revision
и failure episode. Отмена/устаревшая lease не увеличивает failure count, не меняет
node state, метрики и Telegram; задача остаётся due для нового контекста.
Проверка и запись должны быть атомарны относительно переключения: простого if перед
`storeResult` недостаточно. Это распространяется и на глубокую диагностику и access-check.

### 5.5 История и волна проверок

Хранилище результата: `(sourceId, addressFamily, bindingStableId, bindingRevision)`;
каждая запись содержит epoch и observedAt. Текущая валидность зависит от epoch.
Разделять последние измерения и исторические node lifecycle/IP-replacement события:
смена source не равна замене серверного IP и не открывает fake recovery episode.
При смене оператора старые результаты доступны как история прежней сети, но не
подставляются в текущий online/offline. UI показывает «Ещё не проверено в этой сети».

Старые snapshot v1 восстановить как legacy source с историческим контекстом;
пользователь может явно сопоставить их iPhone-профилю, но не объявлять свежими
без новой проверки. Миграция пишет v2 рядом с сохранённым v1 backup и обратима.
Также пересмотреть monitor state, diagnosis/access history, alert episodes и
метрики, а не только `results.json`. В Prometheus стабильный source ID допустим,
но epoch и постоянно меняющийся public IP не добавлять в массовые labels.

После восстановления не устраивать полный синхронный recheck всех привязок:
переиспользовать общий probe budget, fair lanes и небольшие batches с jitter.
Начальный лимит прогрева, например 5 одновременных задач с повышением до заданного
потолка после устойчивых контрольных раундов, — настраиваемая гипотеза.
Network incidents имеют отдельное агрегированное уведомление; во время outage
не создаются тысячи node-down, а после нового source не рассылаются fake node-fixed.

### 5.6 Применение конфигурации

Предлагаемые API, **ещё не реализованы**:
- `GET /api/v1/network` — backward-compatible статус активного источника;
- `GET /api/v1/network/sources` — профили и runtime status;
- `POST /api/v1/network/sources/{id}/validate` — bounded preflight job, не меняет active;
- `POST /api/v1/network/sources/{id}/activate` — отдельный host-control job;
- `GET /api/v1/network/jobs/{id}` — сохранённый статус применения;
- существующий reconnect — только при capability активного источника.

Это локальный управляющий API нашей панели, не Remnawave API. В рамках grooming
внешние API вообще не вызывались; правило только GET для Remnawave сохраняется.

Preflight кандидата проверяет конфигурацию, наличие host-интерфейса, адреса и пересечения
подсетей. Он **не доказывает**, что ещё не подключённый bridge VM работает. Полная проверка
guest route/DNS/egress проходит после переключения bridge, до открытия gate и фиксации
нового active source. Если она не проходит, job возвращает прежнюю конфигурацию.
Для полной проверки кандидата без остановки активной VM потребовался бы отдельный
временный runner/VM; эта дополнительная инфраструктура не включена в MVP.

Смена физического bridge может прервать и саму панель: она работает внутри той же VM.
Панель до переключения сохраняет job ID и показывает ожидаемое переподключение;
host-supervisor пишет durable job status вне VM, клиент после возврата возобновляет poll.
Не обещать, что API внутри остановленной VM продолжит обслуживать запросы.
Для полностью непрерывного UI понадобится отдельный host control-plane — не MVP.

Host-supervisor принимает только типизированные команды и заранее сохранённый source ID,
не произвольные shell/URL/пути из браузера. Существующий world-writable control dir
не масштабировать на расширенное управление: закрытые права, проверка владельца,
authenticated private API, CSRF/origin checks, idempotency key и блокировка перехода.
При изменении профиля во время validate его отчёт становится obsolete по config revision.

## 6. Порядок реализации и критерии готовности

### Этап A — обобщение без смены поведения
Общий source model + UI labels/capabilities; legacy env остаются aliases.
Network monitor и recovery adapter iPhone продолжают работать как раньше.
Результаты/алерты сохраняются; нет миграции железа и продового переключения.

### Этап B — корректность измерений
ProbeContext + атомарный commit, контекстные кэши/хранилища, строгий DNS/source-IP,
семейство адресов, тесты неизвестного/просроченного источника и старых результатов.

### Этап C — router-lan и контролируемое переключение
Discovery/validate, supervisor generic adapter, durable jobs и пауза UI,
отдельный тестовый профиль; ручной приёмочный прогон после подключения железа.

### Приёмочные сценарии

| Эксперимент | Требуемый результат |
|---|---|
| Домашний Wi-Fi работает, кабель LTE-сегмента вынут | Измерения останавливаются; ни одного успешного теста через домашний путь |
| LAN роутера жив, LTE WAN отключён | no_internet/подробные observations; нет массового node-down |
| Роутер имеет проводной резерв | LTE-only сегмент не переключается; иначе required WAN gate закрывается |
| Только DNS отказал | Отдельная DNS ошибка, IP-based control остаётся наблюдаемым |
| Один контрольный сайт недоступен | degraded, а не установленная блокировка всех адресов |
| Sidecar умер / пишет старый JSON | stale и закрытый gate |
| A → B → A, public IP совпал | Новые epochs; результаты/кэш B и старых запросов A не переиспользуются |
| Смена source при активном HTTP/TLS/диагностическом запросе | Старый результат не обновляет state, counters, метрики и alerts |
| CGNAT public IP сменился | После обнаружения новый контекст, без вывода «сменился IP ноды» |
| IPv6 домашнего Wi-Fi доступен | IPv4-only MVP не использует его для успешного измерения |
| В окружении выставлен HTTP_PROXY | Строгий контроль не обходит source через внешний proxy |
| Перезапуск после snapshot v1/v2 | История сохраняется, чужой контекст не становится текущим |
| Переключение bridge завершилось ошибкой | Job failed; возвращается прежняя config, если прежний путь доступен |
| LTE восстановился при тысячах due задач | Ограниченный прогрев; справедливые очереди и отдельный route heartbeat |

Rollback реализации: заранее сохранить source config и snapshots; выключить новые
адмиссионные jobs, вернуть предыдущую версию и совместимый v1 snapshot, восстановить
прежний bridge/источник через supervisor. Не удалять volume и не стирать историю.
Если iPhone физически отсутствует, откат конфигурации не означает восстановление связи:
панель должна честно остаться на паузе. В этом grooming runtime-откат не требуется,
поскольку создаются только документ и демонстрационный макет.

## 7. Открытые решения для следующего обсуждения

1. Модель роутера/прошивка и модема; Mac подключается Ethernet или Wi-Fi?
2. Сегмент будет строго LTE-only? Есть ли другой WAN и автоматический резерв?
3. iPhone остаётся ручным запасным профилем или после миграции убирается?
4. Нужен ли строгий verified WAN через API, либо достаточно проверенной LTE-only топологии?

Рекомендация: начать с отдельного Ethernet-сегмента, ручного выбора одного источника,
без auto-failover, с сохранением iPhone как отдельного неактивного профиля.

## 10. Telegram-алерты — самостоятельный раздел

В полном рабочем макете должны оставаться четыре разных раздела:
**Мониторинг / Сеть проверок / События / Telegram-алерты**.
Уведомления уже являются функцией проекта; редизайн не должен терять существующие
настройки или смешивать внутренний журнал с доставкой сообщений.

В разделе алертов показать:
- Бот и получатель, общее включение доставки. Токен остаётся на сервере и не
  возвращается в браузер. В макете подключение и чат демонстрационные.
- Категории: подтверждённые ошибки привязок, успешное восстановление, смена
  серверного IP, изменение конфигурации, события сети наблюдения.
- Область уведомлений: панели и источники. Смена мобильного public IP не
  переименовывается в замену IP серверной ноды.
- Группировка волны и окно сводки, дедупликация по эпизоду. Предложенные в макете
  интервалы — варианты UX, не утверждение о нынешних параметрах backend.
- Предпросмотр черновика, явное сохранение, отдельный тест доставки через backend.
  В демонстрации тест проверяет только представление и не отправляет запросов.

При реализации: мигрировать сохранённые пользовательские предпочтения, отдельно
сохранять draft и applied settings, применять revision/конкурентное редактирование.
Правила уведомлений не меняют алгоритм диагностики и не превращают одиночный
таймаут в подтверждённый инцидент. Если служебный канал Telegram недоступен,
очередь должна хранить событие и позднее отправлять актуальную сводку/восстановление,
не обещая немедленного сообщения во время обрыва. Старый эпизод не создаёт заново
сотни уведомлений при возврате сети или смене контекста.

Дополнительная приёмка: фильтр панели/источника действительно исключает сообщение;
выключенная категория не отправляется; повторная проверка того же эпизода не
дублирует алерт; сводка не пересчитывает один инцидент несколько раз; тестовое
сообщение не помечается доставленным до ответа канала; переключение измерительной
сети не меняет получателя и не сбрасывает предпочтения.
